# Task Record: 3.3 DegradationController 三级降级

## Summary
internal/orchestrator/degradation.go 落地 DegradationController 三级降级统一决策器（tech-design › Error Handling › LLM 三级降级设计）。DegradeLevel 枚举（L0 正常/L1 模板意图匹配/L2 预置查询入口/L3 明示降级）与 chat 响应 type 枚举（report/preset_entries/degraded_notice，api-handbook §1 严格一致）。Decide(sessionKey, probe, intent, presets)：probe 仅在需要探活时被调用——进入降级后同会话冷却 5min 内不再探活（避免重复消耗 LLM 预算），冷却过期或从未降级才探活，探活成功即回升 L0 并清状态、失败则重置冷却起点并维持降级；逐级尝试、只降不升。decideLevel 纯决策：LLM 不可用时，模板匹配置信度 <0.6（可配）或抽取不出服务名 → L2（preset_entries；预置目录空则落入 L3 degraded_notice），否则 L1（模板报告，规则引擎结论填充）。DegradeDecision.Stamp 将降级级别计入 TraceStep.DegradeLevel（前端徽标依据）。NewDegradationController 支持冷却/阈值/时钟注入，非法参数回退默认（5min/0.6/time.Now）。11 个单元测试全绿，degradation.go 覆盖率 100%。

### Key Decisions
- 降级谓词（超时>12s/连续2次失败/1h 预算耗尽）封装在 probe 闭包内，控制器只管理冷却与级别决策，不感知具体谓词实现（降级谓词由 GuardedLLM/预算追踪器提供）
- 探活检视「冷却窗口内不探活、冷却后探活一次」：probe 在锁外调用避免阻塞并发会话；降级状态 + 进入时刻按 sessionKey 内存化（P1 单实例），回升即 delete、失败即重置冷却起点
- L2 触发（低置信/无服务名）与 L1（规则结论）在 decideLevel 内一次性判定；presets 为空时 L2 自然落 L3 明示降级，绝不返回编造内容
- type 枚举 report/preset_entries/degraded_notice 与 api-handbook §1 逐字一致；DegradeLevel 0..3 递增，作为 TraceStep.DegradeLevel 的唯一映射源（Stamp）
- 控制器输出 DegradeDecision{Level, Degraded, Type}，供 chat 处理器（Phase 4/5 web 层）将 L2/L3 落为 preset_entries/degraded_notice 响应；编排层 RunChat 已覆盖 L0（LLM 解读）/L1（规则降级 + DegradeLevel=1）路径
- cooldown/threshold/now 均可注入（now func() time.Time），使冷却/回升状态机可确定性单测（时间推进模拟冷却过期）
